# Hotpot Roguelike Mechanics Prototype

## Context

I want to prototype a game inspired by **Balatro**, but instead of poker, the player is preparing hotpot for customers.

This is a **mechanics prototype**, not the final game.

The eventual game will likely be made in Godot, but for now I want a very simple **HTML + CSS + JavaScript** prototype.

The purpose of this prototype is to experiment with:

* Ingredient interactions
* Soup evolution
* Ingredient freshness/cooking
* Synergies
* Customer preferences
* Deck/hand decisions
* Rerolls
* Changing/reusing soup
* Different scoring systems
* Whether `points × multiplier` is actually fun for this concept

Prioritize **easy experimentation and iteration** over visual polish or complex architecture.

---

# Core Game Concept

The player prepares hotpot for customers.

The player has:

* A deck of ingredient cards
* A hand of available ingredients
* A cooking pot
* A current soup
* A customer with preferences
* The ability to add ingredients to the pot
* The ability to eventually submit the pot to the customer

The important idea is that the player wants to **reuse the same soup for as long as possible**.

Every ingredient added to the pot can modify the soup.

Possible soup properties:

* Spicy
* Sweet
* Creamy
* Rich
* Umami
* Salty
* Sour

For example:

```text
Chili
    Spicy +4
    Aromatic +2

Beef
    Umami +3
    Rich +2

Milk
    Creamy +3
    Sweet +1
```

The soup should therefore evolve throughout a run.

Changing/replacing the soup should have drawbacks.

Possible penalties include:

* Losing accumulated soup properties
* Losing soup modifiers
* Losing score
* Losing some progress

However, these are experimental. Do not hardcode the design around one particular penalty.

# Prototype Philosophy

Treat this as a **mechanics laboratory**.

I want to quickly test questions such as:

* Is additive scoring more interesting than multipliers?
* Is `points × multiplier` actually appropriate for hotpot?
* Should soup properties act as multipliers?
* Are customer preferences interesting?
* Is it fun to keep ingredients cooking?
* Is freshness an interesting strategic resource?
* Are synergies interesting?
* Is reusing the same soup worth doing?
* Is changing the soup an interesting decision?
* Does the player have enough meaningful decisions each turn?

Therefore:

> Keep the game logic separate from the UI.

> Keep game data separate from game logic.

> Make numbers and rules easy to change.

> Avoid hardcoding individual ingredients, customers, or synergies into the core game loop.

> Avoid premature abstraction.

The simulation should ideally work without the UI.

For example:

```js
const result = game.submitPot();
```

should be able to return a structured result containing:

* Final score
* Score breakdown
* Triggered synergies
* Triggered effects

# Freshness / Cooking

Initially use three states:

```text
Fresh → Cooked → Spoiled
```

Freshness progresses based on turns.

For example:

```text
Fresh:
2 turns

Cooked:
3 turns

Spoiled:
permanent
```

However, freshness timing should be configurable **per ingredient**.

For example:

```text
Beef:
freshDuration = 2
cookedDuration = 3

Tofu:
freshDuration = 3
cookedDuration = 2
```

The exact values are experimental.

Also make the effect of freshness configurable.

For example:

```text
Fresh:
+3 points

Cooked:
+5 points

Spoiled:
-3 points
```

Do not assume these values are final.

The prototype should make it easy to experiment with:

* Freshness durations
* Freshness point modifiers
* Spoiled behavior

```js
{

    properties: {
        spicy: 8,
        sweet: 2,
        creamy: 1,
        rich: 5,
        umami: 9,
        salty: 4
    }
}
```

Ingredients modify these properties.

Soup properties should be data-driven where practical.

I should be able to add/remove/change soup properties without rewriting the entire game.

Conceptually:

## Vegetable

While cooking:

Conceptually:

# Scoring System

## VERY IMPORTANT

The scoring system is **not decided yet**.

Do not build the entire prototype around one scoring formula.

I specifically want to compare different scoring models to determine which one produces the most interesting gameplay.

The scoring system should therefore be **replaceable/pluggable**.

Initially implement at least these models.

---

## Model A — Additive

```text
Ingredient points
+ synergy bonuses
+ customer bonuses
+ soup bonuses

= Final Score
```

---

## Model B — Points × Multiplier

```text
Base ingredient points
+ synergy points

= Points

Points × Multiplier

= Final Score
```

---

## Model C — Soup as Multiplier

```text
Ingredient/synergy points
× soup-based multiplier

= Final Score
```

For example, soup properties could contribute to the multiplier.

---

## Model D — Customer Weighted

Customer preferences directly modify the value of soup properties or ingredients.

For example:

```text
Spicy × 2
Umami × 3
Creamy × 0.5
```

---

## Model E — Thresholds

Soup properties provide bonuses when reaching thresholds.

Example:

```text
Spicy >= 5
    +10

Spicy >= 8
    +25

Spicy >= 10
    +50
```

These formulas are examples only.

Make them easy to modify.

# Suggested Architecture

Please evaluate whether this architecture is appropriate rather than blindly implementing it.

Conceptually:

```text
DATA / MODELS

Ingredient
Soup
Customer
Synergy
Effect
ScoreResult


SYSTEMS

SoupSystem
FreshnessSystem
SynergySystem
CustomerSystem
DraftSystem
ScoringSystem


GAME STATE

GameState


UI

CustomerUI
PotUI
HandUI
DeckUI
EditorUI
DebugUI
```

The important separation is:

```text
Data describes things.

Systems perform operations.

GameState stores the current simulation state.

UI displays state and sends commands.
```

For example:

```text
UI Button
    ↓
game.addIngredient()
    ↓
SoupSystem
    ↓
Effects
    ↓
Synergy evaluation
    ↓
GameState updated
    ↓
UI renders state
```

The UI should not contain gameplay rules.

# Avoid Overengineering

Do NOT automatically create a class/system for every noun.

For example:

* Tags can simply be strings.
* An Ingredient does not necessarily need an IngredientSystem.
* Ingredient instances may not be necessary initially.
* A TriggerSystem should only exist if the number of event-driven interactions actually justifies it.
* Do not build a generic event architecture just because it might be useful later.
* Do not build networking.
* Do not build a backend.
* Do not build authentication.
* Do not build polished animations.
* Do not build a complex card rendering system.

Prefer simple data structures and functions where appropriate.

The prototype exists to discover the game design.
